# Архитектура

## Границы

Один Laravel-проект и один сценарий генерации описания товара. HTTP и очередь используют общие прикладные сервисы. Данные хранятся в MySQL; Redis обслуживает очередь, кеш статистики и rate limiting.

`GenerationController → GenerationService → GenerationRepository → MySQL`

`ProcessGenerationJob → GenerationProcessor → TextGenerator`

`GenerationProcessor → GenerationRepository → MySQL`

Интерфейс введён для изменяемой внешней зависимости — генератора текста. Для репозиториев нет универсального CRUD-интерфейса: их операции выражают конкретные потребности сценария. Eloquent остаётся частью слоя данных, а вход в провайдер и выход из него представлены readonly DTO.

## Создание и идемпотентность

1. Sanctum проверяет токен, middleware — право записи и лимит запросов.
2. Form Request проверяет заголовок и тело. DTO собирается в фиксированном порядке полей; хеш не зависит от порядка ключей JSON. Нормализация пробелов соответствует middleware Laravel. Порядок элементов `features` сохраняется.
3. `firstOrCreate` использует уникальное ограничение `(user_id, idempotency_key)`. Создание одной строки атомарно и выполняется в autocommit. Это позволяет проигравшему конкурентному INSERT увидеть уже закоммиченную запись победителя, не оставаясь в старом снимке MySQL REPEATABLE READ.
4. Хеш параметров сверяется и для существующей записи. Несовпадение даёт `409`.
5. После успешного сохранения отправляется задание с `afterCommit`. В payload очереди передаётся только ID, без текста и ключа провайдера.

Проверка `exists()` перед обычным INSERT без уникального ограничения была бы подвержена гонке. Важное поведение проверяет `MySqlConcurrencyTest`.

## MySQL как источник состояния очереди

Запись `queued` с `available_at` является долговечным намерением выполнить работу. Публикация в Redis — ускоренный путь доставки. Планировщик повторяет публикацию готовых строк, поэтому разрыв между коммитом MySQL и отправкой в Redis восстанавливается без отдельной таблицы outbox.

Компромисс: одна строка описывает один тип работы, период восстановления — до следующего прохода планировщика, а повторная публикация допускается. Для большого числа независимых событий потребовался бы полноценный transactional outbox. Сам `afterCommit` не делает MySQL и Redis одной транзакцией.

## Обработка

Под короткой транзакцией и блокировкой строки воркер проверяет `queued`, время следующей попытки и лимит попыток, переводит запись в `processing` и создаёт `generation_attempts`. Конкурирующий воркер после ожидания блокировки увидит обновлённое состояние и завершится.

HTTP-вызов происходит после коммита. Завершение записывается другой короткой транзакцией. Перед изменением проверяются состояние и номер попытки — устаревший ответ не может перезаписать результат восстановления.

Состояния:

- `queued → processing → succeeded`;
- `processing → queued` при безопасном отложенном повторе;
- `processing → failed` при окончательной ошибке или неизвестном результате.

Время ожидания HTTP — 40 секунд, лимит воркера — 60, Redis `retry_after` — 120, порог прерванной обработки — 300. Порядок этих значений намеренный. Даже при повторной доставке Redis состояние MySQL препятствует повторному вызову для `processing`.

## Ошибки и повторы

| Ситуация | Поведение |
| --- | --- |
| HTTP 429 rate limit | До трёх вызовов, отложенная следующая попытка |
| Исчерпана квота | `quota_exceeded`, без автоматического повтора |
| HTTP 4xx, кроме временного rate limit | `provider_rejected` |
| Таймаут / HTTP 408 / HTTP 5xx | `outcome_unknown`, без автоматического повтора |
| Неполный или некорректный успешный ответ | Отказ с безопасным кодом; известные токены сохраняются |
| Изменились провайдер или модель | `provider_configuration_changed` |
| Воркер исчез в состоянии processing | Через 300 секунд `outcome_unknown` |

Очередь имеет одну автоматическую попытку исполнения Job. Повторы провайдера управляются состоянием MySQL; механизм очереди не повторяет оплачиваемый вызов вслепую.

Гарантия ограничена: невозможно узнать, выполнил ли внешний сервис запрос, если ответ потерян, а API не предоставляет подходящей идемпотентности или сверки результата. Поэтому проект выбирает консервативное завершение. Повторное задание с новым ключом — отдельное намерение пользователя и может привести к повторной оплате.

## Статистика

Одна генерация может иметь несколько попыток. Количество генераций агрегируется отдельно от расхода токенов, иначе JOIN завысил бы количество заданий. Токены суммируются по всем попыткам заданий выбранного периода, включая известный расход неуспешных ответов. Неизвестные значения не объявляются известным нулевым расходом: отдельно возвращается их количество.

Кеш содержит пользователя, начало и конец периода в ключе. TTL 60 секунд устраняет сложную схему инвалидации при явно допустимой задержке статистики. Получение самого задания всегда читает актуальное состояние MySQL.

## Доступ и эксплуатация

Токены имеют срок действия и права чтения/записи. Политика для чужой генерации возвращает `404`; история и статистика фильтруются по текущему пользователю. Публичный ответ не содержит ключ идемпотентности, хеш, user ID, provider request ID или техническое сообщение внешнего API.

Логи приложения содержат ID задания, номер попытки и классификацию ошибки. Адаптер не сохраняет исходное HTTP-исключение с заголовками/телом. Ключ берётся из окружения. В БД сохраняются входной текст и результат; срок хранения и удаление данных должны быть определены перед production-эксплуатацией.

## Проверки решений

- Unit: стабильность хеша, демопровайдер, структура Responses API и классификация ошибок.
- Feature на MySQL: HTTP-контракт, права, идемпотентность, cursor-пагинация, повторы, восстановление и статистика.
- Integration: четыре конкурентных PHP-процесса, настоящий Redis и отдельный процесс воркера.
- Smoke: запросы к работающему приложению через HTTP.
- SQL: воспроизводимый EXPLAIN ANALYZE на синтетических данных; показатели зависят от окружения.
